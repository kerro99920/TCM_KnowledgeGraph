## 一、知识图谱基础

### 1.1 三元组（Triple）

知识图谱的最小知识单元是三元组：**(主体 Subject, 谓词 Predicate, 客体 Object)**。

- 例：`(四君子汤, HAS_INGREDIENT, 人参)`、`(黄芪, HAS_EFFECT, 补气)`。
- 在属性图（Property Graph，Neo4j 的模型）中：主体/客体是**节点**（带 label 和属性），谓词是**有向关系**（也可带属性，如 `HAS_INGREDIENT {dosage: '10g', role: '君药'}`）。
- 与 RDF 三元组的区别：属性图允许节点和边直接挂属性，不必把属性也拆成三元组，更适合工程落地。

### 1.2 本体（Ontology）与 Schema 设计

- **本体**：对领域概念及其关系的形式化约定——有哪些实体类型、哪些关系、关系的定义域(domain)/值域(range)是什么。
- **Schema（模式层）** 是本体的工程化落地。设计要点：
  1. **实体类型收敛**：类型不宜过多，可枚举、边界清晰（本项目 6 类：Herb/Formula/Disease/Symptom/Effect/Source）。
  2. **关系有向且语义单一**：一个关系类型只表达一种语义，方向固定（如 `HAS_INGREDIENT` 一定是 Formula→Herb）。
  3. **属性 vs 节点的取舍**：会被"作为查询目标/共享"的信息建节点（功效建成 Effect 节点才能问"哪些药能补气"）；纯描述性信息作属性（性味、用法）。
  4. **唯一键**：每个节点需要业务唯一键（本项目用 `name` + 唯一性约束）。
  5. **Schema 唯一权威定义**：抽取提示词、导入校验、Text2Cypher 提示词、API 都应引用同一份定义，否则必然漂移（本项目此前的核心病灶）。

### 1.3 模式层 / 数据层

- 模式层：标签、关系类型、属性名、约束（如 `CREATE CONSTRAINT ... REQUIRE n.name IS UNIQUE`）。
- 数据层：具体实例节点与边。
- 构建管线：数据获取（爬虫）→ 信息抽取（LLM/规则）→ 实体对齐 → 入库（批量 MERGE）→ 应用（问答/检索）。

## 二、Cypher 核心语法速查

### 2.1 基本读查询

```cypher
// 精确匹配 + 返回
MATCH (h:Herb {name: '黄芪'}) RETURN h

// 模式匹配（带方向的关系）
MATCH (f:Formula)-[:HAS_INGREDIENT]->(h:Herb {name: '人参'})
RETURN f.name

// WHERE 过滤 + 模糊匹配
MATCH (f:Formula)-[:TREATS_DISEASE]->(d:Disease)
WHERE d.name CONTAINS '感冒'
RETURN f.name, d.name LIMIT 25

// OPTIONAL MATCH：左连接语义，匹配不到返回 null
MATCH (h:Herb {name: '黄芪'})
OPTIONAL MATCH (h)-[r]->(m)
RETURN h, collect({rel: type(r), target: m.name})

// 聚合与排序
MATCH (f:Formula)-[:HAS_INGREDIENT]->(h:Herb)
RETURN f.name, count(h) AS n ORDER BY n DESC LIMIT 10
```

### 2.2 写操作：CREATE / MERGE / SET

```cypher
CREATE (n:Herb {name: '人参'})        // 无条件新建（会重复）
MERGE  (n:Herb {name: '人参'})        // 不存在才建（幂等，先查后建）
MERGE (n:Herb {name: '人参'})
  ON CREATE SET n.created = timestamp()
  ON MATCH  SET n.updated = timestamp()
SET n += $props                        // 批量合并属性（保留未覆盖的旧属性）
```

- **MERGE 陷阱**：`MERGE (a)-[:R]->(b)` 时若 a、b 未先 MATCH/MERGE 到，会连节点一起新建。所以建边前先 MATCH 两端。

### 2.3 UNWIND + 参数化：批量导入模式（本项目 ingest 的核心）

```cypher
// 一条语句写入一批节点，rows 是参数（列表）
UNWIND $rows AS row
MERGE (n:Herb {name: row.name})
SET n += row.props

// 一条语句写入一批关系（先 MATCH 两端再 MERGE 边）
UNWIND $rows AS row
MATCH (a:Formula {name: row.subj}), (b:Herb {name: row.obj})
MERGE (a)-[r:HAS_INGREDIENT]->(b)
```

要点：
1. **参数化**（`$rows`）：防注入 + 查询计划缓存复用，绝不能字符串拼接数据。
2. **UNWIND 批量**：一次网络往返写 N 行，比逐条快一个数量级以上；批大小 500~1000 较稳。
3. **标签不能参数化**：`MERGE (n:$label)` 是非法的，标签只能拼字符串——所以必须配**白名单校验**（`safe_label`），这是拼接唯一可接受的前提。
4. **唯一性约束**先建：既保证幂等，又让 MERGE 走索引。

### 2.4 其他常用

```cypher
MATCH (n) DETACH DELETE n              // 清库（删节点连带删边）
CREATE CONSTRAINT IF NOT EXISTS FOR (n:Herb) REQUIRE n.name IS UNIQUE
MATCH (n) RETURN labels(n)[0] AS l, count(n)   // 按标签统计
MATCH ()-[r]->() RETURN type(r), count(r)      // 按关系统计
```

## 三、Text2Cypher：原理与安全防线

### 3.1 原理

Text2Cypher = 把自然语言问题翻译成 Cypher 的 LLM 任务。提示词三要素：

1. **Schema 注入**：把节点标签、属性、关系及方向描述给模型（本项目由 `graph_schema.schema_prompt()` 自动生成，schema 改了提示词自动跟着改）。
2. **少样本示例**：给 1~3 个"问题→Cypher"对，显著提升方向/标签正确率。
3. **输出约束**：要求 JSON 格式返回 `{"cypher": ..., "explanation": ...}`，便于程序解析。

失败兜底：生成失败/校验不过/查询无结果时，退化为"已识别实体的邻域查询"（按归一化后的实体名精确 MATCH 一跳邻居），保证问答链路不断。

### 3.2 为什么必须有安全防线

LLM 输出不可信：可能被用户诱导生成 `MATCH (n) DETACH DELETE n`，可能幻觉出不存在的标签，可能通过 `CALL` 调用 apoc 过程执行任意操作。**生成的 Cypher 等同于不可信用户输入。**

### 3.3 本项目防线（`database/cypher_guard.py`）

1. **只读校验**：剥离字符串字面量与注释后，按词边界扫描禁用关键字（CREATE/MERGE/DELETE/DETACH/SET/REMOVE/DROP/FOREACH/LOAD/CALL/SHOW...）。先剥字符串是为了不误杀 `WHERE d.name = 'SET综合征'` 这类值。
2. **语句头白名单**：必须以 MATCH/OPTIONAL/WITH/RETURN/UNWIND 开头。
3. **标签/关系白名单**：从节点模式 `(n:Label)` 和关系模式 `[r:TYPE]` 中提取标识符，逐一比对统一 schema；越界即拒绝。
4. **LIMIT 兜底**：无 LIMIT 自动追加 `LIMIT 50`，防止全图扫描拖垮服务。
5. **拒绝反引号**：反引号标识符是绕过标签白名单的常见通道。
6. **纵深防御**：更完整的做法还包括用只读数据库账号连接、EXPLAIN 预检、超时限制——白名单校验是应用层第一道，数据库权限是最后一道。

## 四、实体对齐（Entity Alignment / Resolution）

同一现实实体在不同来源/写法下的提及要合并为图中同一节点，否则图谱碎片化（"北芪"和"黄芪"两个节点，问答只命中其一）。典型三个层次，由浅入深：

1. **精确匹配**：字符串归一化后相等即同一实体。归一化包括：Unicode NFKC（全角→半角）、去空白、异体字/繁简映射（蔘→参）。这是零成本的必做项。
2. **别名表（词典法）**：人工/半自动维护"异名→规范名"映射（北芪→黄芪、元胡→延胡索、国老→甘草）。中医领域异名极多且相对固定，词典法性价比最高。本项目在 `graph_schema.ENTITY_ALIASES` 维护，**导入时**（合并节点、合并属性）与**查询时**（问句实体归一后再查）都过同一个 `normalize_entity_name()`。
3. **Embedding 相似度**：对实体名/描述编码为向量，用余弦相似度 + 阈值（或 ANN 检索 topK 再由 LLM 判别）判断是否同一实体。适合覆盖词典漏网的长尾情况；代价是需要向量模型、阈值调参和人工审核。本项目暂未实现，是明确的下一步扩展位。

补充概念：实体对齐（同库去重）vs 实体链接（把文本提及链到已有知识库条目）——机制相通，方向不同。

## 五、图谱 + RAG 融合（GraphRAG 思路）

RAG = 检索增强生成。图谱在其中是**一路结构化召回**：

1. **向量 RAG**：问题 → embedding → 相似文本块。优点是覆盖广；缺点是多跳推理弱、易拼凑。
2. **图谱 RAG**：问题 → 实体识别/Text2Cypher → 子图/路径。优点是精确、可多跳（"治疗感冒的方剂里都用了哪些药"天然是两跳图查询）、可解释（能给出命中的三元组作为引用）；缺点是覆盖受限于图谱构建质量。
3. **融合模式**（工程上常见）：
   - **并联召回**：向量检索文本 + 图谱检索三元组，拼进同一个 prompt，LLM 综合作答；
   - **串联增强**：先图谱定位实体，再用实体扩展向量检索（或反之）；
   - **路由**：按意图分类决定走哪路（本项目 route 节点即此思路的简化版）。
4. 本项目当前形态：**图谱单路召回的 RAG**——LangGraph 流水线 `route → extract → retrieve(Text2Cypher) → respond`，检索结果格式化为上下文注入回答提示词，同时把执行的 Cypher 与来源实体返回给前端（可解释性）。加向量路只需在 retrieve 阶段并联一路 embedding 检索。

## 六、本项目统一后的架构与 Schema

### 6.1 架构

```
frontend/app.py (Streamlit, 纯 HTTP 客户端)
        │ REST
        v
app/ (唯一核心实现, FastAPI + LangGraph)
  api/routes:  /api/v1/chat  /api/v1/knowledge/{schema,stats,entity,search,query}  /health
  agents:      route → extract(实体归一) → retrieve(Text2Cypher + CypherGuard) → respond
  ingest:      alpaca_import (实体对齐 → 去重 → UNWIND+MERGE 批量导入)
  extraction:  triple_extractor (LLM 三元组抽取, 输出即统一 schema)
  database:    neo4j_client (async) + cypher_guard (安全防线)
  graph_schema.py  ★ 唯一权威 schema：标签/关系/属性/别名表/白名单/提示词生成
```

数据流：`tcm crawl` → 原始文本 → `tcm extract triples` → Alpaca JSON → `tcm db import-alpaca` → Neo4j → API/前端。

### 6.2 统一 Schema

- 节点：`Herb`(中药材)、`Formula`(方剂)、`Disease`(疾病)、`Symptom`(症状)、`Effect`(功效)、`Source`(文献)；唯一键都是 `name`。
- 关系：`HAS_INGREDIENT`(Formula→Herb, 属性 dosage/role)、`TREATS_DISEASE`、`ALLEVIATES_SYMPTOM`、`HAS_EFFECT`(以上三者 Herb|Formula→目标)、`HAS_SYMPTOM`(Disease→Symptom)、`FROM_SOURCE`(Herb|Formula→Source)。
- Herb 属性：alias/property_flavor/meridian/effect/indication/dosage/usage/taboo/origin/place/processing/traits；Formula 属性：alias/effect/indication/usage/taboo。

## 七、收敛重构决策记录（2026-07）

**背景**：仓库里存在两套互不打通、schema 冲突的平行实现——

- 顶层：`common/` + `frontend/app.py` 直连 Neo4j，问答检索是 `n.name CONTAINS 问题前10字` 的关键词匹配；schema 用 Herb/Formula（README、抽取、导入与真实数据一致）。
- `app/`：完整的 FastAPI + LangGraph Text2Cypher 实现，但 schema 用 Medicine/Prescription + TREATS/CONTAINS（与库中数据对不上），且没有任何前端接入。

**决策与理由**：

1. **以 `app/` 为唯一实现**：分层、异步、可测试性都更好；删除顶层 `common/`、`crawler/`、`database/`、`extraction/`、`examples/`、`requirements.txt`。
2. **schema 采用数据侧的 Herb/Formula 体系**：真实图谱数据是按它导入的，改代码比重导数据便宜且无损；`app/` 内的 Medicine/Prescription 全部对齐过来，旧标签仅在 LLM 输出归一时做映射（`LABEL_ALIASES`）。
3. **新增 `graph_schema.py` 作为唯一权威定义**：抽取提示词、导入校验、Text2Cypher schema 注入、API /schema 全部从它生成，杜绝再次漂移。
4. **前端降级为薄客户端**：Streamlit 只调 REST API，删除其中的关键词 CONTAINS 问答路径；问答只剩 Text2Cypher 一条链路（CLI `tcm chat` 也复用同一 agent）。
5. **删除按旧 schema 建模的死代码**：`models/entities.py`、`database/repositories/`、`extraction/extractor.py`（Excel 导入/导出链路一并移除，唯一入库通道是 Alpaca 导入）。
6. **保留并迁移导入脚本的优点**：UNWIND+MERGE 批量、safe_label 迁入 `ingest/alpaca_import.py`，并升级——safe_label 从"字符清洗"升级为"白名单校验"，同时覆盖关系类型与属性键；新增唯一性约束与批次切分。
7. **实体对齐落地为归一化管线**：NFKC → 去空白 → 异体字 → 别名表，导入与查询共用；embedding 相似度层留作展望。
8. **删除未接通的 BGE-M3 语义检索**：`llm/embeddings.py` 从未被调用却引入 sentence-transformers（连带 torch 约数 GB 依赖），删除后依赖大幅瘦身；未来接向量召回时再按需加回。
9. **配置统一**：`.env` 变量名以 `MODEL_*`/`NEO4J_*` 为准，`app` 的 Settings 通过 validation_alias 对齐，单一 `.env.example`。
10. **已修复的存量 bug**：LangGraph 节点里 `AgentState(**state.model_dump(), intent=...)` 会因重复关键字直接 TypeError（改用 `model_copy(update=...)`）；`graph.ainvoke` 返回 dict 却按属性访问（改为字典取值）。

**遗留/展望**：向量召回（实体对齐第三层 + RAG 第二路）、关系属性（dosage/role）在抽取端产出、前端图可视化、只读数据库账号。
